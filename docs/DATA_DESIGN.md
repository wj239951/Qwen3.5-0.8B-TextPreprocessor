# 数据设计

## 为什么不用"人工标注脏文本"

清洗任务的标签有很强的结构：绝大多数变换是**可判定**的（删哪个字符、补不补空格、要不要合并行），
只有极少数边界情况需要语感。用人工或纯 LLM 标注，会为那些本来可以精确计算的部分引入噪声，
而且无法验证"有没有偷偷改写内容"。

因此本项目采用 **规则 oracle + 老师生成** 的双轨制。

## 双轨制

```
                      ┌──────────────────────────────┐
干净种子语料 ──弄脏──▶ │  11 种噪声注入器（noise.py）  │
                      └──────────────┬───────────────┘
                                     │ 脏文本
                                     ▼
                      ┌──────────────────────────────┐
                      │  规则引擎（normalizer.py）    │──▶ 精确标签
                      └──────────────────────────────┘

场景 + 主题 ──提示词──▶ DeepSeek-V4.1-Flash ──▶ 脏文本 + 老师答案
                                     │              │
                                     └──────┬───────┘
                                            ▼
                              ┌───────────────────────────┐
                              │ 与规则 oracle 相似度 ≥0.90 │──▶ 采用（标签仍用 oracle）
                              └───────────────────────────┘
```

### 轨道一：规则合成（约 85%）

1. **种子**：`src/data/seeds.py` 里约 130 条原创干净文本，覆盖中文长段落、中英混排、
   数字单位、URL/邮箱、代码、列表、英文、聊天短句、公文体。
2. **弄脏**：`src/data/noise.py` 的 11 个注入器，与规范里的清洗步骤一一对应。
3. **打标**：直接调用 `clean()`，得到与规范 100% 一致的标签。

样本按两种模式构造：

| 模式 | 占比 | 作用 |
|---|---|---|
| `corrupt` | ~78% | 多噪声叠加，主力样本 |
| `identity` | ~22% | **原样保留**，教模型"干净文本一个字都不要动" |

`identity` 是踩坑之后加的：第一版把"清洗前后没变化"的样本全部丢弃了，结果模型学会了
"凡输入皆要动手"——把合法的 `刚刚` 压成 `刚`、给短句凭空补字。对清洗模型来说，
"不动"和"动手"同样是需要学习的动作。

训练数据里**没有乱码样本**。原因见 `TRAINING.md` 坑 5：0.8B 模型学不会字节级还原，
只会记住"看到乱码就输出某段中文"，进而在真实输入上编造整段内容。乱码修复由
`repair_mojibake()` 在调用链前面完成。

关键性质：**噪声可逆**。`tools/check_invertibility.py` 对每个注入器做
"clean(corrupt(x)) == clean(x)" 的自检，11 个注入器当前均为 100%。
这意味着标签不是"标注"出来的，而是"算"出来的——没有标注噪声，且完全可复现。

### 轨道二：老师生成（约 15%）

规则合成有个天然短板：语言分布是种子语料的子集，噪声组合也偏"干净"。
所以让 DeepSeek-V4.1-Flash 按 16 种真实场景（网页复制、PDF 折断、微信转发、代码混排、
语音转写、客服工单……）现场造脏输入。

老师同时会给出它认为的清洗结果，但**不直接采用**：

- 用规则 oracle 清洗同一段脏文本；
- 计算两者字符相似度，低于 0.90 直接丢弃（说明老师越界改写了，或规则有盲区）；
- 采用后标签仍取 oracle 的结果，老师的答案只作为"分布校验"。

实测 1200 条请求里 970 条通过（拒绝率 **19%**），拒绝原因：

| 原因 | 条数 |
|---|---|
| clean 与 raw 长度比例异常（老师在解释而不是清洗） | 61 |
| raw 本身已经干净，无需清洗 | 36 |
| 与规则 oracle 分歧过大（老师把中文标点改成半角等） | 61 |

这条校验挡住的不只是"格式不一致"，还有**幻觉**：老师面对一段字节被截断的乱码时，
会"猜"出原文（例如把 `æ˜Žå¤©å‡ºå‘` 猜成"明天出发"）。那是编造，不是修复——
规范明确不修无法验证的乱码，学生也就不该学这个动作。

## 混合比例

| 来源 | 条数（repeat=2 后） | 占比 | 作用 |
|---|---|---|---|
| 规则合成 | 12000 | ~85% | 教会机械变换的边界 |
| 老师生成 | 2400 | ~15% | 教会自然分布的脏文本长什么样 |

## 防泄漏

按**种子**划分 train/valid/test：同一篇种子的所有变体只会落在同一个集合。
老师和规则数据的测试集都单独生成，训练时不可见。

## 数据规模的经验值

- 少于 3k：0.8B 模型能学会删零宽字符，但中英混排的标点判断会不稳；
- 8k–15k：本任务的甜点，验证集 loss 在第 1.5 个 epoch 后基本不再下降；
- 多于 30k：收益很小，反而更容易过拟合到种子语料的表达方式。
